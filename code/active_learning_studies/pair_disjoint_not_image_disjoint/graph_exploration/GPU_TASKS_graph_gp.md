# GPU / lab tasks left for the user — graph-kernel Gaussian-process reward model

Everything in this study is CPU-only (frozen SimCLR features, kernels on ~1.1k nodes, one thread, 0.3 s per GP fit). What needs more:

1. **Deep-kernel GP (end-to-end encoder + GP head).** The GP here uses a fixed RBF kernel on frozen SimCLR features; its win over the MLP head comes from locality (near-duplicate lookup), and the NNGP kernel of the head's own function class (arc-cosine) is *worse* (dev: AUC 0.935 vs 0.948). Learning the kernel's feature map (deep kernel learning / fine-tuned encoder with the graph-deformed GP head, trained on GPU with inducing points) is the natural next lever; evaluate with the standard endpoint plus the anchor-far stratum and the time-blocked split.
2. **A better encoder for the kernel and the graph** (DINOv2 / CLIP are not reachable from the container; ImageNet ResNet and SimCLR layer 3 were null in the representation branch): re-tune the length scale ℓ (0.25 x median distance here) and re-run the grid in `gp_grid.py`; the GP fit is so cheap that the grid is a few CPU minutes.
3. **New growth runs with pairwise judgments (lab task).** The unresolved question is generalisation to a new run: the time-blocked split of the red team is the closest available test and is reported in `RESULTS_graph_gp.md`. A prospective, fully held-out run would also show whether the GP's near-duplicate advantage survives when no near-duplicate frame exists.
4. **Bayesian use of the posterior (needs the lab loop):** the GP posterior over scores could drive batch acquisition and Bayesian optimisation of growth conditions. In the simulated protocol the predictive sd was not informative about errors (AUROC 0.3 for predicting an error from the sd, because sd grows with the score margin), so a calibrated uncertainty needs a better noise model first.
